LESSON 0 — BEFORE THE FIRST LINE OF CODE

What is software, really?

Before you write a single "Hello, World," it helps to know what you're actually stepping into — and why it's more interesting than it looks from the outside.

THE IDEA

A list of instructions, taken very seriously

At its core, software is nothing more than a list of instructions for a machine that has no imagination, no guessing, and no patience for ambiguity.

When you build a website, you're already writing instructions — "put this text here, make this button blue, do this when clicked." Software development is the same idea, stretched further: instructions for handling money, flying planes, matching people on dating apps, or running the servers this very page is stored on.

What makes it hard isn't the individual instructions — those are simple. What makes it hard is organizing thousands of them so a human can still understand what's going on a year later. That's the entire craft. Not "can you make the computer do the thing," but "can you make the computer do the thing in a way that doesn't collapse when it grows."

FUN FACT

The word "bug" for a software error predates software. In 1947, engineers at Harvard found an actual moth stuck in a relay of the Mark II computer, jamming it. They taped it into the logbook. It's in the Smithsonian today.

WHY IT'S HARD

The computer isn't the problem. You are.

A computer will do exactly what you tell it, every single time, without complaint. That sounds easy — until you realize it means every bug is your fault. Not the machine's. Yours.

Most of software development is really about managing complexity — the way small, simple pieces combine into something too big to hold in your head all at once. A single "if" statement is trivial. A hundred of them, tangled together, talking to a database, waiting on a network, handling a user who clicks the wrong button at the wrong time — that's where real skill lives.

This is why concepts like design principles and architecture exist. They're not academic decoration. They're survival tools — techniques experienced developers built after getting burned by their own messes, so the next person (often themselves, six months later) doesn't drown in it.

FUN FACT

The first computer "programmer" is widely considered to be Ada Lovelace, who in 1843 wrote an algorithm for a machine that was never actually built in her lifetime — the Analytical Engine. She was writing software before there was hardware to run it on.

A GLIMPSE AHEAD

Why "good" code is a design choice, not an accident

Two developers can solve the exact same problem and produce code that behaves identically — yet one version is easy to change next month, and the other quietly punishes anyone who touches it. The difference usually isn't cleverness. It's whether the code was shaped with a few simple ideas in mind: keep related things together, keep unrelated things apart, and don't repeat yourself if you can help it.

You'll meet these ideas properly later — things like separation of concerns, or the "single responsibility" idea, where each piece of code should really only have one job. For now, just notice the pattern: good software design is less about being smart, and more about being kind to your future self.

FUN FACT

NASA's coding standards for the Space Shuttle's flight software were so strict that the team went years at a stretch without a single bug reaching production — a level of discipline that came entirely from process and design principles, not raw talent.

CHECK YOURSELF

A few questions to sit with

Q1 If a computer only does exactly what it's told, where do bugs actually come from?
From the gap between what you meant and what you actually told it. The machine isn't wrong — your instructions were incomplete, or handled a case you didn't think of.
Q2 Why would a project need "design principles" at all — isn't working code enough?
Working code today doesn't guarantee working code after ten more features get bolted on. Design principles exist to keep code changeable, not just functional — because almost all software keeps growing after it "works."
Q3 What's the real skill in software development — writing code, or something else?
Managing complexity. Writing a line of code is easy. Organizing thousands of lines so they stay understandable, months later, by you or someone else, is the actual craft.
YOUR FIRST ASSIGNMENT

No code yet. Just noticing.

Before Hello World, spend 15–20 minutes doing this — pen and paper, or a notes app, whatever's easiest.

  • Pick one app you use daily (banking app, WhatsApp, a game — anything). Something you didn't build and don't know the inner workings of.
  • Write down 5 things it does that feel simple to you as a user, but probably require several "instructions" behind the scenes. Example: "shows me my new messages instantly" — that's actually the app checking a server, comparing data, and updating your screen, likely many times a minute.
  • For just one of those 5, guess (don't research) what could go wrong if the instructions were written carelessly. What's the "bug" that might happen? What would the user see?
There's no code to write here — the goal is just to start noticing that every smooth experience you use is hiding a pile of careful instructions underneath. That instinct is worth more, early on, than syntax.
